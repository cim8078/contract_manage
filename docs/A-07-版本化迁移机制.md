# A-07 版本化迁移机制（schema_version）

> 目标：建立数据库结构版本化迁移机制——新增 `schema_version` 版本记录表，将 `init_db()` 中散落的 ad-hoc `ALTER TABLE` 迁移（资金来源/是否归档/归档人/归档时间、列改名、用户分管部门等）改写为按版本号顺序执行且幂等的迁移脚本列表，使结构变更可追溯、可重复执行。
> 背景：改动前结构变更靠 `init_db()` 内 ad-hoc `ALTER TABLE`（含历史兼容逻辑），无版本记录，无法审计与回滚；每次新增列/改名都只能继续向 `init_db()` 追加判断代码。

**1. 修改范围**
- 仅修改 `app.py` 的 `init_db()` 及新增的模块级迁移辅助函数；未改变任何业务接口行为与前端页面。
- 迁移机制在 `init_db()` 内最先执行（`_SCHEMA` 之后、A-01~A-06 各约束块之前），保证后续约束块始终作用在“已补齐历史列”的结构上。
- A-01~A-06 仍为 `init_db()` 内一次性幂等约束块（唯一索引/复合主键/外键/CHECK/NOT NULL/索引/触发器），未纳入版本列表，保持任务范围不变；后续新增结构变更按约定向 `MIGRATIONS` 追加新版本号。

**2. 数据库结构修改（新增 1 张版本表）**

```sql
CREATE TABLE IF NOT EXISTS schema_version (
  version INTEGER PRIMARY KEY,
  applied_at TEXT,
  description TEXT
);
```

- 每次迁移成功后在事务内写入一行 `(version, applied_at, description)`；`applied_at` 为执行时间，`description` 为迁移说明，供审计。
- 实测当前库 `schema_version` 3 行：v1/v2/v3（应用时间一致，见第 4 节）。

**3. 迁移执行机制（_run_versioned_migrations）**
- 读取已应用版本集合 `applied`；仅执行 `version > 当前最大已应用版本` 的迁移，已应用版本一律跳过（幂等）。
- 每个迁移在独立 `BEGIN…COMMIT` 事务中执行：先执行迁移函数，成功后写入版本记录再提交；任一步失败则 `ROLLBACK`、不记录版本并向上抛出错误（下次启动自动重试）。
- 启动时检测到版本落后即自动执行，`app.log.err` 输出 `[MIGRATE] schema_version <版本>: <说明>` 日志。
- 迁移函数本身保持幂等（列存在性判断），删除版本行可强制重跑对应版本。
- 约定：新增结构变更只向 `MIGRATIONS` 追加新版本号，禁止修改已执行的历史版本。

**4. 迁移版本明细（v1 ~ v3）**

| 版本 | 说明 | 迁移内容 |
|---|---|---|
| 1 | contracts 追加历史字段列 | `资金来源`/`是否归档`/`归档人`/`归档时间`（存在即跳过） |
| 2 | contracts 历史列改名 | `经办人/分管领导`→`经办人`、`甲方现场负责人`→`现场负责人` |
| 3 | users 追加分管部门字段 | `分管部门`（存在即跳过） |

```python
MIGRATIONS = [
    (1, "contracts 追加历史字段列：资金来源/是否归档/归档人/归档时间", _mig_v1_contract_extra_cols),
    (2, "contracts 列改名：经办人/分管领导→经办人、甲方现场负责人→现场负责人", _mig_v2_contract_rename_cols),
    (3, "users 追加 分管部门 字段", _mig_v3_users_supervise_dept),
]
```

- 说明：当前 `_SCHEMA` 新库 DDL 已含上述全部列，v1~v3 在新库与已升级库上均为“无实际 DDL 变更、仅写入版本记录”；在手工构造的旧结构库上仍能验证真实的补列/改名逻辑。

**5. 数据库记录修改（0 条）**
- 本机制仅做结构迁移与版本记录，不修改任何业务数据；v1~v3 在当前库上为幂等空操作，639 条合同、27 条用户、6 条附件、部门数据均未改动。
- 全新库种子数据（admin 用户、默认部门、默认配置）由原有 `_seed_defaults()` 写入，与版本化迁移解耦。

**6. 解决的问题**
- 改动前：结构变更散落在 `init_db()` 内的 ad-hoc `ALTER TABLE`，无版本记录、无法审计、无法单独重放/回滚。
- 改动后：每次启动自动按版本号顺序补齐未应用的结构迁移，`schema_version` 提供完整审计轨迹；删除某版本行即可单独重跑该版本（迁移幂等）。
- 行为不变：登录、合同新增/修改/删除/归档/导入/导出、提醒、待支付、统计、部门、用户、附件等接口与前端均不受影响。

**7. 验收结果（已实测）**
1. 全新库首次启动：3 个迁移全部执行一次，`schema_version` 行数与迁移数一致（3 行），种子数据正常，无报错。
2. 已存在库二次启动：无重复执行（不打印 `[MIGRATE]`），版本号不变（仍 3 行），全部幂等。
3. 手工模拟旧库升级：构造缺 资金来源/是否归档/归档人/归档时间、含旧列名（经办人/分管领导、甲方现场负责人）、users 缺 分管部门 的旧结构库，首次启动后补列+改名成功、数据完整保留、版本记录 3 行；二次启动幂等。
4. 回滚重放：删除 `schema_version` 中 v2 行后重跑，仅 v2 重新执行，版本恢复为 v1/v2/v3，无副作用。
5. 线上回归：服务重启后 `app.log.err` 输出 3 条 `[MIGRATE]` 且无 ERROR/Traceback；登录、仪表盘、合同列表/详情、提醒、待支付、统计、部门、用户、日志、导出（xlsx）、新增+删除合同全流程回归正常。

**8. 附带修复（全新库首次启动的外键报错）**
- 问题：全新库首次启动在 `_seed_defaults()` 报 `sqlite3.IntegrityError: FOREIGN KEY constraint failed`。
- 原因：A-03 外键改造后，`trg_users_dept_sync_i` 触发器会在插入用户后把 `所属单位/所属科室` 从 `所属部门` 字符串回填（外键列），而原种子逻辑先插用户后插部门，空 `departments` 表导致回填值无法通过外键校验。
- 修复：调整 `_seed_defaults()` 插入顺序为先插部门（湘潭市机关事务管理局本级-办公室）再插用户，外键列回填后即可命中部门行；不影响任何业务接口与已有数据。

**9. 回滚方式**
- 删除版本行即可强制重跑对应版本（迁移本身幂等）：

```sql
DELETE FROM schema_version WHERE version = <版本号>;
```

- 结构变更的整体回滚仍依赖数据库备份：本次重启前备份为 `backups/合同台账_版本迁移重启前_20260823_202631.db`；如删除 `schema_version` 表，下次启动会按 `MIGRATIONS` 全量重跑一次。
