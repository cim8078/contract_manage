## 一、系统概述

“潭合同”台账管理系统是湘潭市机关事务管理局内部使用的合同台账管理软件，用于合同信息的新增、修改、删除、查询、统计、导出，以及重新采购到期提醒。

- **部署形态**：单机轻量级 Web 应用，后端 Flask，前端单页 HTML（Vue 3 + Bootstrap 5，依赖全部本地化），数据存储 SQLite。
- **代码规模**：后端 `app.py` 约 83 KB（全部业务逻辑与 API），前端 `templates/index.html` 约 128 KB（单页应用）。
- **数据规模**：当前约 639 条合同、27 个用户、13 个部门组合、6 个附件记录。

## 二、技术架构

### 2.1 技术栈

| 层次 | 技术 | 说明 |
|------|------|------|
| 前端 | Vue 3（组合式 API）、Bootstrap 5、Chart.js、SheetJS、Bootstrap Icons | 单文件 `templates/index.html`，依赖本地化于 `static/vendor/`，无外网依赖 |
| 后端 | Python 3.8+ / Flask | `app.py` 提供全部 REST API，基于 Session 认证 |
| 数据存储 | SQLite（`data/合同台账.db`） | 七张业务表：合同、用户、部门、配置、附件、操作日志、schema_version（数据库版本记录表） |
| Excel | openpyxl | 模板下载、查询导出、日志导出、首次启动数据迁移 |
| 并发控制 | 线程锁（`threading.Lock`）+ SQLite | 写操作串行化，保证数据一致 |

### 2.2 请求处理流程

1. 浏览器加载 `/` → 返回 `templates/index.html`；
2. 前端 Vue 应用启动，调用 `/api/current_user` 恢复会话；
3. 各页面通过 `fetch` 调用后端 REST API（前缀 `/api`）；
4. 后端装饰器 `@login_required` / `@admin_required` 校验会话与角色；
5. 列表、统计、提醒、导出统一经 `_scope_contracts()` 做数据权限过滤；
6. 所有写操作前执行 `_backup()` 自动备份数据库，并调用 `write_log()` 写入审计日志。

### 3.3 其他表结构

**users**：用户名（TEXT，主键）、密码（TEXT，SHA256 哈希）、姓名、所属部门、角色（管理员/普通用户/查询用户）、分管部门（TEXT，顿号分隔，领导岗位用）、所属单位、所属科室（外键 → departments（单位名称, 科室名称），由触发器同步，A-03）。

**departments**：单位名称、科室名称（复合主键（单位名称, 科室名称），A-02）。

**settings**：配置项（TEXT，主键）、配置值（TEXT）。当前配置项：`default_remind_days`（默认 60）、`log_keep_days`（默认 90）、`default_attach_max_mb`（默认 20）。

**attachments**：附件ID（TEXT，主键，UUID）、合同编号（外键 → contracts.编号，A-03）、附件类型（决策依据附件/合同附件/验收结算附件）、显示名称、存储文件名（UUID.扩展名）、文件大小（INTEGER，字节数，A-06）、上传人、上传时间。

**operation_logs**：id（主键）、时间、用户名、姓名、角色、IP、模块、操作类型、对象、详情、结果。仅追加写入，无修改/删除接口。

**schema_version**：version（INTEGER，主键，已应用的迁移版本号）、applied_at（TEXT，应用时间）、description（TEXT，变更说明）。由 `_run_versioned_migrations()` 自动维护，当前 3 行（v1/v2/v3，A-07）。

## 四、后端设计

### 4.1 认证与授权

- **会话**：Flask Session（`session["username"]`），Cookie SameSite=Lax，会话常驻（`session.permanent=True`）；
- **装饰器**：`@login_required` 校验已登录；`@admin_required` 校验管理员角色；
- **数据权限**：
  - 管理员：全部合同可见可写；
  - 普通用户/查询用户：可见 = 本部门 + 分管部门（`_visible_depts()`），列表、统计、提醒、导出统一经 `_scope_contracts()` 过滤；
  - 写权限：`_can_write()` 限制普通用户仅可操作可见部门合同；
  - 归档权限：管理员或该合同经办人（`_split_names()` 解析多人）。

### 4.2 审计日志

- `write_log(module, action, obj="", detail="", result="成功")` 在关键操作处调用；
- 记录时间、用户、姓名、角色、IP（优先取 `X-Forwarded-For`）、模块、操作类型、对象、详情、结果；
- 日志只追加；`_cleanup_logs()` 按 `log_keep_days`（默认 90 天）定期清理；
- 日志导出（管理员）动作自身留痕。

### 4.3 自动备份

- 每次写操作（`db_exec`、`app_row`、`write_attachments`）前调用 `_backup()`；
- 备份到 `backups/合同台账_YYYYMMDD_HHMMSS.db`，保留 30 天自动清理。

### 4.5 关键实现说明

- **编号唯一性**：新增/修改均遍历全表校验“编号”不重复；
- **提醒计算**：`next_bid_date - remind_days ≤ today` 且合同属于用户可见范围 → 进入提醒列表（含已归档合同）；剩余天数 = 下次招采时间 − 今天；
- **待支付计算**：`_pending_unpaid()` 优先取台账“未支付”字段（含 0），为空时按“合同金额 − 已支付”计算（空按 0）；`_pending_count()` 统计未归档且待支付金额大于 0 的合同数；`/api/pending_payments` 与待支付项目数卡片口径一致，按“未归档 + 待支付金额大于 0”筛选；
- **附件校验**：格式白名单（jpg/jpeg/png/gif/webp/bmp/pdf）+ 大小限制（`default_attach_max_mb`，默认 20M，可在系统设置调整），超限拒绝并清理临时文件；
- **导入校验**：`_check_import_row()` 检查必填、编号重复（库内/文件内）、数字与日期格式、枚举、部门存在性，返回 通过/警告/错误 三级；必填校验与库表 NOT NULL 对齐（`IMPORT_REQUIRED` 7 项 + 编号/项目名称单独校验，9 个必填字段为空即 error）；`api_import_contracts` 执行导入捕获 `sqlite3.IntegrityError`，返回 400 中文友好提示；
- **Excel 兼容**：列名归一化（`_norm_header`）兼容“端工验收时间”“经办人/分管领导”“甲方现场负责人”等历史表头。

#### 数据库版本化迁移（schema_version）

- 版本记录表 `schema_version(version, applied_at, description)`，记录已应用的迁移版本（当前 3 行 v1/v2/v3）；
- `MIGRATIONS` 按版本号顺序登记迁移（当前 3 项）：v1 contracts 补历史字段列（资金来源/是否归档/归档人/归档时间）、v2 contracts 列改名（经办人/分管领导→经办人、甲方现场负责人→现场负责人）、v3 users 补分管部门；
- `_run_versioned_migrations(con)` 机制：建表 → 读取已应用版本 → 按版本号顺序执行未应用迁移 → 每个迁移独立事务，成功后写入版本记录并输出 `[MIGRATE]` 日志 → 失败回滚且不记录版本（下次启动重试）；
- 幂等：迁移函数自带存在性判断，删除版本行可强制重跑对应版本；
- 新增结构变更必须向 `MIGRATIONS` 追加新版本号，禁止修改已执行的历史版本（A-07）。

#### A-01~A-08 数据库完整性规范化落地清单

| 编号 | 内容 | 落地方式 |
|------|------|----------|
| A-01 | 合同编号唯一约束 | 唯一索引 `idx_contracts_no`（先扫描拦截存量重复编号） |
| A-02 | departments 复合主键 | 表重建为（单位名称, 科室名称）复合主键 |
| A-03 | 外键与同步触发器 | contracts/users 外键 → departments；`PRAGMA foreign_keys=ON`；触发器 trg_contracts_dept_sync_i/u、trg_users_dept_sync_i/u、trg_departments_rename_sync；修复 71 条部门数据 |
| A-04 | 常用查询列索引 | 5 个索引：idx_contracts_department / idx_contracts_procurement_date / idx_contracts_next_bid_date / idx_contracts_archived / idx_contracts_handler |
| A-05 | contracts 重建 CHECK/NOT NULL | 9 必填 NOT NULL、5 金额列 CHECK ≥ 0、5 日期列 GLOB CHECK（yyyy-mm-dd）；枚举 CHECK 延后未启用 |

## 五、前端设计

### 5.1 总体结构

- 单文件应用，Vue 3 全局构建（`vue.global.prod.js`），无构建步骤、无 npm 依赖；
- 状态管理：`store = reactive({ user, dashboard, reminders, config })`；
- 视图切换：`currentView`（home / contracts / stats / users / depts / settings / logs），菜单点击触发 `switchView()`；
- API 封装：`api(method, path, body)` 统一处理 JSON、错误与 401 跳转。

### 5.2 视图与功能

| 视图 | 功能 |
|------|------|
| home | 五张统计卡片（总合同数/总合同额/已将到期/待支付项目数/待支付总金额）、合同到期提醒列表（忽略/永久关闭、更多/折叠）、待支付提醒列表（动态数量说明、更多/折叠） |
| contracts | 搜索筛选、分页表格、新增/编辑弹窗、删除、归档、附件上传、导出、导入预览与执行、打印为PDF |
| stats | 九个统计维度（部门/时间/经办人/项目分类/资金来源/部门支付情况/项目支付情况/部门预算执行情况/项目预算执行情况）、筛选控件一行排列、统计/重置按钮、四种图表类型、统计明细表、导出 |

### 5.3 表单与校验

- `defaultForm` 定义合同表单 28 字段；`formErrors` 记录字段级错误；
- `validateContractForm()` 前端校验必填、金额、日期格式；
- 附件选择走 `onAttachSelect()`，前端白名单 `ATTACH_ALLOWED`；
- 删除/归档/清空提醒使用统一确认框 `showConfirm()`（支持 `needReason`）。

### 5.4 打印为PDF实现

- `printContractPdf()` 从当前合同弹窗的 `contractForm` 直接读取数据（不二次加载），保证打印内容与页面一致；
- 通过 `window.open('', '_blank')` 打开新标签页并 `document.write()` 生成独立打印文档（内嵌 CSS，无系统导航/侧边菜单）；弹窗被拦截时回退为隐藏 iframe 打印；
- 打印文档采用 A4 `@page` 与紧凑字体（11px 表格、`page-break-inside:avoid`）保证单条合同 1 页内完成；
- 水印层 `.wm`：`打印人：{登录用户姓名}　打印时间：YYYY-MM-DD HH:mm:ss`，12px、浅灰、透明度 15%、`rotate(-45deg)` 固定定位覆盖整页，`print-color-adjust:exact` 确保打印预览与 PDF 可见；
- 新窗口 `window.print()` 自动触发打印预览。

**本地修改推送到 GitHub**

```
git status                 # 查看工作区变更，确认同步范围
git add -A                 # 暂存全部修改（backups/、cookies.txt、日志等已被 .gitignore 排除）
git commit -m "变更说明"    # 生成一次提交记录
git push                   # 推送到 GitHub
```

也可以使用一键脚本（项目根目录）：

```
.\sync.ps1                    # 自动生成提交说明并推送

```

**从 GitHub 拉取更新**

```
git pull
```

**同步规则**

- 提交前先执行 `git status` 核对变更范围，避免误提交；
- 提交说明用一句话概括本次变更（如“新增资金来源字段”“修复导出日期格式”），便于版本回溯；
- `backups/`（历史数据库快照）、`cookies.txt`、运行日志、`__pycache__/`、`.playwright-cli/` 等已在 `.gitignore` 中排除，禁止使用 `git add -f` 强制提交；
- `data/` 下的数据库与附件属于仓库内容，会随提交同步到 GitHub；仓库为公开可见，注意不得将账号口令等敏感信息写入代码、数据或文档；
- 本地与远程出现冲突时（`git pull` 提示 conflict），打开冲突文件保留正确内容，再执行 `git add` + `git commit` 完成合并；
- 数据库结构变更仍遵循 7.3 的 MIGRATIONS 版本化规则（追加新版本号、禁止修改历史版本），与代码变更一并提交；
- 文档变更（本文档、《数据字典表》《用户操作手册》）与对应代码变更尽量在同一提交中完成。
