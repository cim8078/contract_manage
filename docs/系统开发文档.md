## 一、系统概述

“潭合同”台账管理系统是湘潭市机关事务管理局内部使用的合同台账管理软件，用于合同信息的新增、修改、删除、查询、统计、导出，以及重新采购到期提醒。

- **部署形态**：单机轻量级 Web 应用，后端 Flask，前端单页 HTML（Vue 3 + Bootstrap 5，依赖全部本地化），数据存储 SQLite。
- **代码规模**：后端 `app.py` 约 179 KB（全部业务逻辑与 API），前端 `templates/index.html` 约 197 KB（单页应用）。
- **数据规模**：当前项目合同 639 条、资产合同 5 条、用户 29 个、部门组合 15 个、项目合同附件 6 条、资产合同附件 1 条、操作日志 794 条、字段级变更日志 0 条。

## 二、技术架构

### 2.1 技术栈

| 层次 | 技术 | 说明 |
|------|------|------|
| 前端 | Vue 3（组合式 API）、Bootstrap 5、Chart.js、SheetJS、Bootstrap Icons | 单文件 `templates/index.html`，依赖本地化于 `static/vendor/`，无外网依赖 |
| 后端 | Python 3.8+ / Flask | `app.py` 提供全部 REST API，基于 Session 认证 |
| 数据存储 | SQLite（`data/合同台账.db`） | 十一张业务表：项目合同、资产合同、资产租金收缴、用户、部门、配置、项目合同附件、资产合同附件、短信模板、短信发送流水、操作日志、字段级变更日志，外加 schema_version（数据库版本记录表） |
| 短信对接 | Python 标准库（`urllib.request` + `hashlib`） | 政务短信平台下发与签名计算，**未引入第三方依赖**；后台守护线程承担每周定时提醒 |
| Excel | openpyxl | 模板下载、查询导出、日志导出、首次启动数据迁移 |
| 并发控制 | 线程锁（`threading.Lock`）+ SQLite | 写操作串行化，保证数据一致 |

### 2.2 请求处理流程

1. 浏览器加载 `/` → 返回 `templates/index.html`；
2. 前端 Vue 应用启动，调用 `/api/current_user` 恢复会话；
3. 各页面通过 `fetch` 调用后端 REST API（前缀 `/api`）；
4. 后端装饰器 `@login_required` / `@admin_required` 校验会话与角色；
5. 列表、统计、提醒、导出统一经 `_scope_contracts()`（项目合同）/ `_scope_assets()`（资产合同）做数据权限过滤；
6. 所有写操作前执行 `_backup()` 自动备份数据库，并调用 `write_log()` 写入审计日志。

索引（5 个）：`idx_asset_rent_collections_contract`、`idx_asset_rent_collections_pay_date`、`idx_asset_rent_collections_period_start`、`idx_asset_rent_collections_period_label`、`idx_arc_contract_period`（资产合同ID + 收款期次，v18 新增）。
接口字段映射由 `ASSET_RENT_FIELDS`（asset_id/period_label/period_start/period_end/due_amount/paid_amount/pay_date/pay_method/payee）维护，校验常量 `ASSET_RENT_REQUIRED`（period_label、due_amount 必填）、`ASSET_RENT_NUM_KEYS`、`ASSET_RENT_DATE_KEYS`、`ASSET_RENT_PAY_METHODS`（枚举）、`ASSET_RENT_MAX_ROWS=200`。

**asset_attachments**（资产合同附件，v9 新增）：附件ID（TEXT，主键，UUID）、资产合同ID（INTEGER，NOT NULL，外键 → asset_contracts(id)，ON DELETE/UPDATE RESTRICT）、附件类型（**三种**：`资产现状图片`（接口键 `condition`，仅图片格式）/`决策依据附件`（`decision`）/`合同附件`（`contract`））、显示名称、存储文件名、文件大小、上传人、上传时间；索引 `idx_asset_attachments_contract`。

**field_change_logs**（字段级变更日志，v11 新增）：id（主键）、时间、用户名、姓名、角色、IP、模块（合同台账 / 资产合同台账）、对象编号、对象名称、字段、原值、新值；索引 `idx_field_logs_object`、`idx_field_logs_time`。由 `log_field_changes()` 写入，仅记录实际发生变化的字段。
> 字段命名约定：主表字段直接使用列名；**资产租金明细**的修改记为 `租金明细[收款期次]·列名`（如 `租金明细[2026年第1季度]·实缴金额（元）`），整条新增/删除记为 `租金明细[收款期次]`（原值/新值记摘要）。数值同值不同写法（`0` 与 `0.0`、`150000` 与 `150000.0`）由 `_same_number()` 判定为未变更，不再产生噪声日志。

**operation_logs**：id（主键）、时间、用户名、姓名、角色、IP、模块、操作类型、对象、详情、结果。仅追加写入，无修改/删除接口。

**schema_version**：version（INTEGER，主键，已应用的迁移版本号）、applied_at（TEXT，应用时间）、description（TEXT，变更说明）。由 `_run_versioned_migrations()` 自动维护，当前 28 行（v1~v28）。

## 四、后端设计

### 4.1 认证与授权

- **会话**：Flask Session（`session["username"]`），Cookie SameSite=Lax，会话常驻（`session.permanent=True`）；
- **装饰器**：`@login_required` 校验已登录；`@admin_required` 校验管理员角色；
- **数据权限**：
  - 管理员：全部合同可见可写；
  - 普通用户/查询用户：可见 = 本部门 + 分管部门（`_visible_depts()`）；项目合同经 `_scope_contracts()`（按“所属部门”）过滤，资产合同经 `_scope_assets()`（按“管理部门”）过滤，两套口径对称；
  - 写权限：`_can_write()` 限制普通用户仅可操作可见部门合同（项目合同）；资产合同的写操作仅限制查询用户（其余角色可增删改），部门可见范围仅约束**读取**；
  - 归档权限：项目合同为管理员或该合同经办人；资产合同为管理员或该资产合同责任人（`_split_names()` 解析多人）。

### 4.2 审计日志

- `write_log(module, action, obj="", detail="", result="成功")` 在关键操作处调用；
- 记录时间、用户、姓名、角色、IP（优先取 `X-Forwarded-For`）、模块、操作类型、对象、详情、结果；
- `log_field_changes(module, obj_no, obj_name, old_vals, new_vals, fields=None)` 记录**字段级**变更（逐字段比较，仅记录发生变化的字段，一个字段一行）到 `field_change_logs`；任何异常均吞掉，不影响主流程；
- 日志只追加；`_cleanup_logs()` 按 `log_keep_days`（默认 90 天）定期清理（操作日志与字段级变更日志共用该保留策略）；
- 日志导出（管理员）动作自身留痕。

### 4.3 自动备份

- 每次写操作（`db_exec`、`app_row`、`write_attachments`）前调用 `_backup()`；
- 备份到 `backups/合同台账_YYYYMMDD_HHMMSS.db`，保留 30 天自动清理。

### 4.5 关键实现说明

- **合同编号生成与唯一性**：新增项目合同/资产合同时，若请求未携带编号，则由 `contract_no.py` 按《合同编号规则》生成 6 位编号（详见 4.7），再遍历全表校验不重复；请求显式携带编号时（历史导入等）沿用原校验逻辑；
- **提醒计算**：项目合同 `_reminders()` 按 `下次招采时间 − 提醒提前天数 ≤ today` 且“所属部门”属于用户可见范围（含已归档合同）；资产合同 `_asset_reminders()` 按 `下次出租时间 − 提醒提前天数 ≤ today` 且“管理部门”属于用户可见范围；`_all_reminders()` 合并两者并按剩余天数升序返回（`kind` 区分 project/asset）；
- **项目合同字段校验（V1.8.2/V1.8.3）**：`_validate_contract_fields(vals, current=None)` 统一校验并规范化「日期 / 金额 / 枚举」三类字段——日期列（采购时间/开工时间/完工时间/竣工验收时间/下次招采时间）经 `_norm_date_ymd()` 接受 `yyyy-m-d`、`yyyy/m/d`、`yyyy.m.d` 并规范化为 `yyyy-mm-dd`，无法解析（如 `2026-13-40`、`2026-02-30`）返回 400（此前直接落库触发 CHECK 异常 → HTTP 500）；金额列（决策的招标控制价/合同金额/结算金额/已支付/未支付）必须 `float()` 可解析且 ≥0（此前「约三万」等文本会被原样入库）；枚举列（项目分类/采购方式/资金来源/是否结算（含「部分结算」）/是否有签证或变更）必须取标准值。**编辑场景传入 `current`（库内原值）：与库内逐字相同的字段跳过校验并回填原值**，避免存量脏数据（金额文本等）所在的记录被锁死无法编辑其它字段；
- **首页卡片口径**：`total_contracts` = 项目合同数 + 资产合同数；`total_amount` = 项目合同“合同金额（万元）”合计 + 资产合同“总合同额”合计 ÷ 10000；`expiring_contracts` = 项目提醒条数（`_project_reminder_count()`）+ 资产提醒条数（`_asset_reminder_count()`）——两函数与 `_reminders()`/`_asset_reminders()` 同口径，但只数条数、不构造明细对象，且资产侧复用已按部门过滤的列表；**待收/支**：待支沿用 `_pending_unpaid()`/`_pending_count()`（仅项目合同），待收＝按资产合同汇总 `Σ应缴金额 − Σ实缴金额`（`read_assets()` 计算列 `due_total − paid_total`），卡片显示待收+待支的合计，悬停气泡显示两者构成占比；
- **只读结果缓存**：`read_contracts()` / `read_assets()` 使用进程内 TTL 缓存（`READ_CACHE_TTL = 2.0s`），同一页面加载中 dashboard / reminders / pending_payments 只读一次库；每次返回**浅拷贝**（调用方可安全挂载 `attachments`/`rent_collections` 等字段而不污染缓存）；写操作（`db_exec`、`app_row`、合同导入、`replace_asset_rent`）调用 `_invalidate_caches()` 立即失效；
- **租金明细保存**：`replace_asset_rent(rid, items, allow_clear)` 以“整表替换”语义在一个事务内完成新增/修改/删除；未出现在 items 中的已有记录被删除；`allow_clear=False` 且 items 为空而该合同已有记录时抛错（防“明细未加载就保存”的清空误操作，接口层由 `confirm_clear` 控制）；保存后调用 `_log_rent_collection_changes()` 写字段级变更日志；
- **字段级变更日志**：`log_field_changes()` 在项目合同/资产合同的新增、修改、归档、清空提醒处调用，并在**资产租金明细保存**后由 `_log_rent_collection_changes()` 调用（逐字段记录修改；整条新增/删除记一条摘要）；逐字段比较新旧值并写入 `field_change_logs`；`_same_number()` 使 `0` 与 `0.0` 这类同值不同写法不再记为变更；`/api/field_logs` 支持日期、用户、模块、字段名、对象筛选；
- **待收/支计算**：待支侧 `_pending_unpaid()` 优先取台账“未支付”字段（含 0），为空时按“合同金额 − 已支付”计算（空按 0），`_pending_count()` 统计未归档且待支付金额大于 0 的项目合同数；待收侧按资产合同汇总租金子表差额（`read_assets()` 计算列 `due_total − paid_total`，>0 计入合同数、差额合计计入金额）；`/api/pending_payments` 同时返回两类记录（`kind=receivable/payable`，待收在前）与 `receivable_count`/`payable_count`，与首页“待收/支合同数/总金额”卡片同口径；
- **附件校验**：项目合同与资产合同共用同一套规则——格式白名单（jpg/jpeg/png/gif/webp/bmp/pdf）+ 大小限制（`default_attach_max_mb`，默认 20M，可在系统设置调整），超限拒绝并清理临时文件；资产合同附件类型为**三种**：`资产现状图片`（仅图片）/`决策依据附件`/`合同附件`，类型非法时返回“收到的 type + 服务端支持列表”（便于识别“服务端未重启”）；
- **导入校验**：`_check_import_row()` 检查必填、编号重复（库内/文件内）、数字与日期格式、枚举、部门存在性，返回 通过/警告/错误 三级；必填校验与库表 NOT NULL 对齐（`IMPORT_REQUIRED` 7 项 + 编号/项目名称单独校验，9 个必填字段为空即 error）；`api_import_contracts` 执行导入捕获 `sqlite3.IntegrityError`，返回 400 中文友好提示；
- **资产合同导入校验**：`_asset_vals()` 统一做必填（place/asset_name/tenant）、数字非负、日期格式校验，导入预览 `import/preview` 逐行返回可导入/不可导入及原因；归档列不参与导入导出；
- **Excel 兼容**：列名归一化（`_norm_header`）兼容“端工验收时间”“经办人/分管领导”“甲方现场负责人”等历史表头。

#### 数据库版本化迁移（schema_version）

- 版本记录表 `schema_version(version, applied_at, description)`，记录已应用的迁移版本（当前 **31 行，v1~v31**）；
- `MIGRATIONS` 按版本号顺序登记迁移（当前 **31 项，v1~v31**）：v1 项目合同补历史字段列（资金来源/是否归档/归档人/归档时间）、v2 项目合同列改名（经办人/分管领导→经办人、甲方现场负责人→现场负责人）、v3 users 补分管部门、v4 新增 asset_contracts、v5 contracts→project_contracts 改名（同步索引/触发器名与外键引用）、v6 asset_contracts 补管理部门/责任人、v7 asset_contracts 补归档列、v8 asset_contracts 补下次出租时间/总合同额、v9 新增 asset_attachments、v10 asset_contracts 补提醒提前天数、v11 新增 field_change_logs、**v12 新增 asset_rent_collections（租金收缴子表，不迁移历史已缴租金）、v13 删除 asset_contracts 的 10 个旧租金列（重建表）、v14 列改名 年租（元）→年租金（元）、v15 删除合同级缴款方式、v16 收缴表缴款方式枚举化并规范化存量值、v17 收缴表缴款方式默认值“直缴非税”、v18 统计/提醒索引（4 个）、v19 users 追加 电话 字段、v20 settings 追加短信平台配置（14 项）、v21 新增 sms_templates（5 个默认模板）、v22 新增 sms_logs（含回执/回复字段与“同一提醒同一周同一手机号”去重唯一索引）、v23 project_contracts/asset_contracts 追加「短信提醒」开关列、v24 settings 追加短信超时项 sms_timeout_sec、v25 settings 追加平台使用规范配置（7 项）、v26 asset_contracts.id 改为 6 位合同编号 TEXT（重建表，历史 id 原值保留）、v27 删除部门表历史残留行「本级-人事与政策法规科」、v28 项目合同附件表改名 attachments → project_attachments、v29 短信正文末尾署名配置 sms_sign_suffix、v30 删除已废弃配置项 sms_sign_name、v31 project_attachments 外键由 ON UPDATE RESTRICT 改为 ON UPDATE CASCADE（重建表，修复“带附件的合同改编号报 500”）**；
- **重建表类迁移的事务约定**：**v13/v15/v17/v26/v31** 需要 `DROP/RENAME` 被外键引用的表，而 `PRAGMA foreign_keys` 在事务内设置无效，故这些版本在 `MIGRATIONS` 中以第 4 个元素 `{"own_transaction": True}` 标记——运行器不套外层事务，由迁移自行“关外键 → BEGIN → 重建 → `PRAGMA foreign_key_check` → COMMIT → 恢复外键 ON”；其余版本沿用默认（运行器统一 `BEGIN/COMMIT`）。**v31 另在重建前用 `VACUUM INTO` 自动整库备份到 `backups/合同台账_v31重建前_<时间戳>.db`**（与 A-03/A-06 的重建流程一致）；
- `_run_versioned_migrations(con)` 机制：建表 → 读取已应用版本 → 按版本号顺序执行未应用迁移 → 每个迁移独立事务，成功后写入版本记录并输出 `[MIGRATE]` 日志 → 失败回滚且不记录版本（下次启动重试）；
- 幂等：迁移函数自带存在性判断，删除版本行可强制重跑对应版本；
- 新增结构变更必须向 `MIGRATIONS` 追加新版本号，禁止修改已执行的历史版本（A-07）。

### 4.6 短信提醒模块（V1.5 新增）

**平台对接**：湘潭市政务短信服务平台，接口前缀 `https://sms.xtdzzw.cn/api`（可在设置中修改）。系统统一调用 **`POST /message/smsBatch`**（点对点批量：一个号码一条内容一个 `guId`），单个收件人亦走批量接口，实现统一链路。

**签名算法**（见对接文档 4.2）：取本次请求的全部标量参数（`accessKey`、`timestamp`、`desAddr`、`msgContent`、`guId` 等），按参数名 ASCII 升序拼接为 `k=v&k=v…`，末尾追加 `key={SecretKey}`，整体做 **MD5 后转大写**：`sign = MD5(sortedParams + "&key=" + SK).toUpperCase()`。其中 `sign` 本身与数组字段 `sendData` **不参与签名**；纯 Python 标准库实现（`hashlib` + `urllib.request`），**未引入第三方依赖**。

**收件人解析**（`_sms_default_receivers`）：

- 项目合同：**经办人**（多值按 `、/;` 拆分）+（到期场景）**现场负责人**；
- 资产合同：**承租人**（取合同自身“联系电话”）+ **责任人**；
- 经办人 / 现场负责人 / 责任人按姓名**精确匹配** `users.姓名` 取其 `users.电话`；号码统一规范化为 11 位手机号并**按号码去重**；
- 解析落空（无电话 / 姓名匹配不到用户）时不发送，并在 `sms_logs` 留一条失败痕迹。

**每周定时任务**：`_sms_scheduler_loop()` 以守护线程运行，每 30s 检查一次；当“周几（ISO 1=周一）+ 时 + 分”命中且当天未执行时触发一次，触发前先把当天日期写入 `settings.sms_last_run_at` 占位以防重复执行。任务整体在 `_sms_lock` 下串行执行。

**去重与留痕**：定时提醒的每条消息写入 `sms_logs` 时带上“周去重键”`{场景}|{关联类型}|{关联ID}|{手机号}|{ISO年-周}`，由部分唯一索引 `idx_sms_logs_dedup` 保证**同一提醒同一周同一手机号仅一条**（“每人一条”）；手动催办 / 点对点 / 重发的去重键为空，按次发送。`guId` 采用 `SMS{流水id}`，回执与回复可据此精确回写。

**错误处理**：`_sms_err_text()` 将底层异常统一翻译为可操作中文（连接超时 / 域名解析失败 / 连接被拒 / 网络不可达 / TLS 握手失败 / HTTP 错误码），并把原始错误附在括号内；失败原因写入 `sms_logs."错误信息"`。连接与读取超时由 `settings.sms_timeout_sec`（默认 10 秒，1~120）控制。

**配置项**：见《数据字典表》第 7 节（`settings` 的 `sms_*` 共 14 项，迁移 v20/v24 写入）。

**平台使用规范合规校验（V1.5.1 新增，`_sms_content_issue` / `_sms_split_content` / `_sms_precheck`）**

| 平台注意事项 | 系统实现 |
|---|---|
| 1 内容不宜过长，需分解多条 | `_sms_split_content()` 按 `sms_segment_len`（默认 70 字）在标点处拆分，超出 `sms_max_segments`（默认 3 段）则拒绝；拆分后每段各自生成一条流水（周去重键加 `#n` 后缀） |
| 2 内容不得含「【】」（多签名阻断） | `_sms_sign_content()` **在正文末尾追加机构署名**：取 `settings.sms_sign_suffix`（默认「（湘潭市机关事务管理局）」，**全角括号**），由 `sms_include_sign` 控制开关，幂等（结尾已带该署名则不重复追加）；**不输出中括号**。发送前 `_sms_content_issue()` 命中「【」或「】」即拦截；模板与署名文本保存时同样拒绝 |
| 3 不得含敏感词 | 按 `sms_block_check` / `sms_block_words` 逐词匹配，命中即拦截并回报命中的词 |
| 4 号码须为有效手机号 | `_sms_mobile()` 仅接受 11 位手机号（`1[3-9]\\d{9}`），固话/虚拟号直接拦截 |
| 5 同一号码每日 ≤100 条 | `_sms_precheck()` 统计该号码当日 `状态='成功'` 条数，达到 `sms_daily_per_phone`（上限 100）即拦截 |
| 6 需限制重复发送间隔 | `_sms_precheck()` 取该号码最近一次成功发送时间，间隔小于 `sms_min_interval_sec`（默认 30 秒）即拦截；判定基于“批次开始前状态”，故周一自动提醒中同一人的多条提醒不会被互相限流 |

被拦截的号码不写流水，通过接口返回 `blocked: [{phone, name, reason}]`，前端在发送结果区逐条展示；失败记录“重发”时会自动清理历史内容中的「【】」后发送。

**配置项**：见《数据字典表》第 7 节（`settings` 的 `sms_*` 共 22 项，迁移 v20/v24/v25/v29 写入）。

### 4.7 合同编号生成规则（6 位统一编号，V1.6 新增）

**规则出处**：2026-10 统一后的《合同编号规则》。规则实现集中在独立模块 `contract_no.py`（规则表 + 前缀解析 + 顺序号计算），由 `app.py` 调用；配套文档为 `docs/合同编号规则.md`。

**编号格式（6 位字符串，前导零不丢失）**

```
第 1-2 位 年度（年后两位，2026 -> "26"）
第 3   位 科室（中心）序号
第 4   位 中心组室序号
第 5-6 位 顺序号（同一“年度+科室（中心）+中心组室”前缀下从 01 连续递增，不足两位左补 0）
```

**第 3 位：科室（中心）序号（统一后名称）**

| 第 3 位 | 科室（中心） | 说明 |
|------|------|------|
| 1 | 办公室 | 局本级 |
| 2 | 国有资产科 | 局本级（原“国有资产管理科 / 资产科”） |
| 3 | 公共事务科 | 局本级（原“公共事务管理科”） |
| 4 | 人事科 | 局本级（原“人事与政策法规科”拆分） |
| 5 | 财务科 | 局本级（原“财务管理科”） |
| 6 | 后勤中心 | 原“市机关后勤服务中心” |
| 7 | 资产中心 | 原“市行政事业单位国有资产事务中心（市国资中心）” |
| 8 | 公车中心 | 原“市公车中心” |
| 9 | 政策法规科 | 局本级（原“人事与政策法规科”拆分） |

**第 4 位：中心组室序号**

| 第 3 位 | 中心组室取值 |
|------|------|
| 1、2、3、4、5、9（局本级科室） | 统一为 `1` |
| 6（后勤中心） | 1=综合组，2=公车组，3=工程组，4=物业组，5=后勤组，6=市民之家专班，7=周转住房专班 |
| 7（资产中心） | 1=综合组，2=房地资产组，3=通用资产组，4=集采组 |
| 8（公车中心） | 1=现场负责组 |

**顺序号（第 5-6 位）**：同一“年度 + 科室（中心）+ 中心组室”前缀下，取对应表中该前缀既有最大顺序号 **加 1**；该前缀下暂无记录时从 `01` 开始；取值范围 `01`~`99`，超过 `99` 抛 `OverflowError`（提示“需扩展编号规则”，不生成错误编号）。

**示例（2026 年）**：后勤中心物业组 `266401`、资产中心综合组 `267101`、资产中心房地资产组 `267201`、资产中心通用资产组 `267301`、资产中心集采组 `267401`、公车中心现场负责组 `268101`、政策法规科 `269101`、国有资产科 `262101`。

**生成流程**

1. 前端：打开「新增项目合同」/「新增资产合同」弹窗时调用 `GET /api/contract_number/next?kind=project|asset[&dept=…]` 获取预览编号并显示在编号栏（编号栏**一律只读**，禁止手工填写）；资产弹窗切换“管理部门”时会按新归属重新预览；
2. 后端：`POST /api/contracts` 将编号写入 `project_contracts."编号"`；`POST /api/asset_contracts` 将编号写入 `asset_contracts.id`；请求未携带编号时按规则生成，携带时（历史导入等）沿用原唯一性校验；
3. 编辑态：项目合同与资产合同的编号栏**同样只读**（V1.6 起统一锁定），保存时原编号原样回写、不会被改动；资产合同编号即主键 `id`。

**规则解析（`contract_no.py`）**

| 名称 | 作用 |
|------|------|

### 5.4 打印为PDF实现

**同步规则**

- 提交前先执行 `git status` 核对变更范围，避免误提交；

- `backups/`（历史数据库快照）、`cookies.txt`、运行日志、`__pycache__/`、`.playwright-cli/` 等已在 `.gitignore` 中排除，禁止使用 `git add -f` 强制提交；

- 本地与远程出现冲突时（`git pull` 提示 conflict），打开冲突文件保留正确内容，再执行 `git add` + `git commit` 完成合并；
- 数据库结构变更仍遵循 7.3 的 MIGRATIONS 版本化规则（追加新版本号、禁止修改历史版本），与代码变更一并提交；
- 文档变更（本文档、《数据字典表》《用户操作手册》）与对应代码变更尽量在同一提交中完成。
