# 「潭合同」台账管理系统 上线前全面测试报告（V2.0）

- **报告日期**：2026-10-12
- **被测版本**：V1.8.3（代码基线 `f951c78` + 本次修复）
- **被测对象**：Flask 后端 `app.py`、前端 `templates/index.html`、SQLite `data/合同台账.db`（schema v1~v31）
- **测试方式**：文档/代码走读 + 独立 Python 脚本（`requests` + `sqlite3` + `openpyxl` + `concurrent.futures`），逐模块执行并断言
- **隔离原则**：全程使用 `backups/` 只读复制到 `test_data/` 的测试库与运行时副本，**生产库未被读写**（每轮校验 size/mtime/sha256 指纹）

## 一、测试概述

### 1.1 范围

覆盖 L1 数据库迁移 → L2 权限/项目合同/资产合同/租金收缴/短信 → L3 首页卡片/提醒/统计 → L4 数据质量 → L5 附件/导入导出/打印 → L6 安全/审计 → L7 性能，共 **16 个模块 208 个用例**。

### 1.2 方法

- **黑盒**：真实 HTTP（隔离副本服务，端口 5099）+ 状态码/响应体断言；
- **白盒**：库内行/字段级断言（sqlite3）、`field_change_logs`/`operation_logs` 断言、关键函数直调（短信合规层）；
- **独立期望值**：`tests/_oracle.py` 按《系统开发文档》《数据字典表》口径**二次实现**，与接口返回值比对，避免照抄被测代码；
- **故障注入**：迁移失败回滚、v31 真实重建路径、缓存写后失效等。

### 1.3 环境

| 项 | 值 |
|---|---|
| Python / 依赖 | 3.14.6；flask 2.3.3、openpyxl、requests 2.34.2 |
| 数据库 | SQLite（测试基线取自 `backups/合同台账_20261012_223429.db`，schema v30→v31） |
| 数据规模 | 项目合同 673、资产合同 5、租金明细 16、用户 54、部门 22、附件 6+2、操作日志 1107 |

## 四、性能结论（M15，实测）

判定标准：**单次请求 < 2s；并发成功率 > 99%**。

| 场景 | 实测 | 结论 |
|---|---|---|
| 首页 dashboard | avg 16ms / max 23ms（n=10，缓存态） | 远优于阈值 |
| 合同列表（673 行） | page_size=20 avg 18ms；=200 avg 27ms | 优 |
| 合同详情 | avg 28ms / max 49ms（n=10） | 优 |
| 统计（项目/资产） | avg 9ms / 13ms | 优 |
| 项目导出 | 161ms / 0.15MB | 优 |
| 单次写操作（含整库备份 1.10MB） | **36ms**（对照热读 31ms） | 当前规模无瓶颈 |
| 10 并发读列表 | 成功率 **100%**、总耗时 72ms | 达标 |
| 只读缓存 | TTL 2s，窗口内 3 次快照完全一致；**写后立即读到新值**（无 sleep） | 语义正确 |

**风险提示**：每次写操作都会整库复制一份备份（≈1.1MB，文件名按秒去重，30 天自动清理）。实测运行目录已累积 **141 个备份文件（≈155MB）**。当前规模无影响，但**批量导入/高频写**场景下 I/O 与磁盘占用会放大，建议上线后评估（与 V1.0 报告观察项一致）。

## 五、安全结论（M13）

**实测通过**

- 未登录访问 **52 个受保护接口全部 401**（仅登录与短信回调按设计豁免）；
- 越权全面拦截（编辑 403、详情 404 隐藏、附件下载/删除 403、用户列表仅本人），资产附件同样按"管理部门"过滤；
- **SQL 注入**：登录 4 组注入式口令均 401；5 处筛选参数均按字面量匹配（参数化生效）；
- **路径穿越**：附件下载与 `/static/../app.py`、`/../app.py`、`/data/合同台账.db`、`/backups/` 均**无法读取源码或数据库**；
- 上传服务端白名单（exe/php/svg 一律 400）；现状图片已按类型硬校验；
- 错误响应统一 JSON，无堆栈/内部信息泄露；短信回调 token 可配置且校验生效；
- 日志只追加（无 DELETE 路由），保留 90 天自动清理实测生效。

**遗留风险（文档已列为 P1 计划项）**

| 风险 | 现状 |
|---|---|
| 会话密钥硬编码在源码 | 建议环境变量化 |
| 口令为 SHA256+固定盐（无迭代/加盐随机） | 建议 PBKDF2/bcrypt |
| 无登录失败锁定或延时 | 实测连续 6 次错误口令仍可正常登录（失败已留痕） |
| Cookie 缺少 `Secure` | 内网 HTTP 部署下属预期，建议 HTTPS 后开启 |
| `data/`（真实库与附件）随公开仓库同步 | 建议迁移为私有仓库或移出仓库 |

## 八、上线建议

**结论：核心功能与数据正确性已具备上线条件（208 例通过 207，仅 1 例为待决策项 D-14，无致命缺陷）。**

**必须项（上线前）**

1. 决策并处理 **D-14**（关闭短信总开关，或明确白名单与责任人）；
2. 首次以新代码启动前**手工备份** `data/合同台账.db`（启动会自动应用迁移 v31 并留"重建前"备份）；
3. 提交本次代码与文档改动至 Git（便于回滚）。

**建议项（可并行/上线后尽快）**

4. 按清洗清单处理 D-15 与 246 处金额文本（优先"控制价单位错位"，否则建议暂不将预算执行维度用于决策）；
5. 落实安全 P1 四项（会话密钥环境变量化、口令哈希升级、登录失败锁定、仓库数据移出公开仓库）；
6. 人工目视验收打印版式（单页 A4、水印、资产附租金明细）。

**可延后**

8. 写前整库备份策略优化（改为差异备份/仅结构变更前备份）；
9. 导入/导出与批量写场景的压测（当前规模无瓶颈）。
