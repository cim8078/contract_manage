# 《数据库规范化评估报告》

> 系统名称：“潭合同”台账管理系统
> 使用单位：湘潭市机关事务管理局
> 版本：V1.0（2026年8月）
> 评估性质：只读评估，评估过程中未对系统功能、代码与文档做任何修改
> 评估对象：`data/合同台账.db`（SQLite，共 6 张业务表）

---

## 一、评估范围与方法

- **评估范围**：系统全部 6 张业务表（contracts、users、departments、settings、attachments、operation_logs）的表结构、字段类型、约束、索引及存量数据特征。
- **评估方法**：以关系数据库第一范式（1NF）、第二范式（2NF）、第三范式（3NF）、BCNF 及通用设计规范为基准，结合 `PRAGMA table_info` 实测与存量数据统计逐项核对。
- **数据规模（2026-08 实测）**：合同 639 条、用户 26 人、部门组合 13 个、附件 6 条、操作日志 331 条。
- **系统形态**：单机轻量级 Web 应用，后端 Flask（`app.py` 1605 行、36 个路由），前端单页 HTML（`templates/index.html` 1607 行），数据存储 SQLite。

## 三、规范化问题诊断

### 3.1 第一范式（1NF）违规——属性非原子

- **经办人多值**：`contracts.经办人` 以中文顿号分隔多人（实测存在“曾富华、欧阳源涵”），无法按单人做数据库级查询、统计与权限判断，需依赖 `_split_names()` 内存解析。
- **分管部门多值**：`users.分管部门` 同样以顿号分隔多个部门（实测“综合组、公车管理组”等多值样例），权限过滤需内存拆解。
- **所属部门复合属性**：`contracts.所属部门`、`users.所属部门` 将“单位名称”与“科室名称”两个属性拼为单串“单位名称-科室名称”，且存量存在 71 条缺科室后缀的不规范值。
- **期限无结构**：`contracts.期限` 为自由文本，实测并存 `2021.1.21-2022.1.30`、`2021年10月28日-2022年10月27日`、`自2022年03月04日至2022年03月07日止`、`质保期一年` 等 200+ 种写法，无法按起止日期查询、统计或校验。
- **子属性平铺**：`签证或变更情况` 依赖 `是否有签证或变更`（子属性放平表），且两列全库为空，属“结构预留但未启用”的死列。

### 3.2 第二、第三范式（2NF/3NF）违规——依赖与传递依赖

- **派生字段冗余**：`未支付` 可由“合同金额 − 已支付”推导（传递依赖），且与“结算金额、已支付”存在勾稽矛盾风险；现系统不得不在多处维护“优先取字段、为空则计算”的双口径。
- **字符串外键**：`contracts.所属部门`、`users.所属部门`、`users.分管部门`、`contracts.归档人`、`attachments.上传人` 均为对 departments/users 的“字符串外键”，无数据库约束保障，删除部门或用户可能产生悬空引用。
- **附件引用不稳定**：`attachments.合同编号` 逻辑关联 `contracts.编号`，合同编号一旦修改需应用层同步改附件（现有代码已实现该“手工维护引用完整性”逻辑），存在遗漏风险。

### 3.3 其他数据库设计规范问题

- **无约束兜底**：全库无任何索引、外键、CHECK、NOT NULL；`contracts.编号` 唯一性仅在应用层校验，绕过 API 写入即可能破坏；`departments` 无主键。
- **中文列名入库**：全部业务列名为中文（如“合同金额（万元）”），所有 SQL 需引号包裹，后续改名、SQL 化统计、第三方工具对接成本高。
- **类型不规范**：`attachments.文件大小` 存 TEXT（应为 INTEGER）；`决策的招标控制价`、`合同金额（万元）` 等数值列部分历史值为文本（数据字典标注 43 条非数字）；日期列均为 TEXT 且格式混杂。
- **枚举无字典表**：项目分类、采购方式、是否结算、资金来源等均无枚举字典表与约束，存量存在大量非标准写法。
- **无版本化迁移机制**：无 schema 版本表，历史结构变更靠 `init_db()` 内 ad-hoc `ALTER TABLE` 拼装，不利于审计与回滚。
- **无记录级时间戳**：业务表无 created_at/updated_at，记录变更只能依赖 operation_logs 审计。

## 四、修改建议（分三档）

### 4.1 档位 A：完整性规范化（建议必做，系统功能基本不动）

- `contracts.编号` 建 UNIQUE 索引；`departments` 建复合主键（单位名称+科室名称）。
- 为 `attachments→contracts`、`users→departments`、`contracts→departments` 建立外键（SQLite 需开启 `PRAGMA foreign_keys`，删除部门/用户前先校验引用）。
- 增加索引：`编号`、`所属部门`、`经办人`、`采购时间`、`下次招采时间`、`是否归档`。
- 增加 CHECK 约束：金额 ≥ 0、日期格式统一、枚举白名单；增加 NOT NULL（必填字段）。
- 类型修正：`文件大小` 改 INTEGER；日期列统一 `YYYY-MM-DD` 并清洗存量。
- 新建 `schema_version` 表，迁移脚本化、幂等化。
- 枚举清洗：按《数据字典表》标准值清洗存量非标准值（需业务确认映射，113/409/12 条）。

### 4.2 档位 B：结构规范化（建议按需，约一半功能需适配）

- **部门拆表**：contracts/users 改存 `department_id` 外键，显示名由 departments 拼接生成。
- **多值拆表**：新建 `contract_handlers(合同, 经办人)`、`user_managed_depts(用户, 部门)` 关联表，替换 `_split_names()`/`norm_managed()` 内存拆解逻辑。
- **期限拆列**：`期限` 拆为 `开始日期`、`结束日期` 两列，存量 200+ 写法需智能解析或人工确认。
- **派生字段**：建议 `未支付` 改为视图或统一计算口径（涉及首页卡片、待支付提醒、统计三处），或保留列 + 触发器保证一致性。

### 4.3 档位 C：深度规范化（量力而行，当前数据量不建议全做）

- 列名英文化（如 `contract_no`、`contract_amount`），建立“英文标识 ↔ 中文显示名”映射层，替换 `CONTRACT_COLUMNS`/`c2r`/`fm` 三处核心映射。
- 建枚举字典表（项目分类/采购方式/资金来源/附件类型/操作类型…）、支付流水表（替代“已支付/未支付/结算金额”平铺）、归档历史表。
- 权限模型表化（角色-权限表）；统计下推 SQL 层；引入 DAO/ORM 层收敛散落的 `db_query` 调用。

## 五、改造工作量评估

以单机 639 行合同、后端 `app.py` 1605 行/36 路由、前端 `index.html` 1607 行单页应用为前提，按模块估算（人天）：

| 模块 | 档位 A | 档位 B | 主要改动说明 |
|------|--------|--------|--------------|
| 迁移脚本与存量数据清洗 | 2–3 | 3–5 | 约束建立、枚举清洗、期限/部门拆分解析、回滚方案 |
| 后端数据读写层 | 0.5–1 | 2–4 | `read_contracts`/`c2r`/`fm`/`upd_row`/`app_row` 映射改造 |
| 后端 API（增删改查/导入导出/统计/提醒/待支付/权限/附件） | 0.5–1 | 4–6 | 部门、经办人、派生金额口径全链路适配 |
| 前端（表单/列表/搜索/统计/导入预览/打印） | 0.5 | 4–6 | `contractForm` 与各视图绑定改造 |
| Excel 模板/导出/导入校验 | 0.5–1 | 1–2 | 列映射与枚举校验适配 |
| 备份/恢复/日志兼容 | 0.5 | 0.5–1 | 整库文件备份方案基本不受影响 |
| 全功能回归（3 角色、导入导出往返、提醒、统计、打印） | 1–2 | 2–4 | 口径一致性重点回归 |
| 文档同步（数据字典/开发文档/操作手册） | 0.5–1 | 1–2 | — |
| **合计** | **约 6–10 人天** | **约 17–30 人天** | 档位 C 另需 15–25 人天，总计可达 30–50 人天 |

### 5.1 主要风险点

- **编号双重身份**：`编号` 既是业务唯一键，又是附件关联键；拆表或加约束前需冻结“改编号”逻辑，避免悬空附件。
- **未支付口径**：删除或调整 `未支付` 会波及首页卡片、待支付提醒、统计三处，必须先统一口径再动数据。
- **枚举标准化依赖业务**：113/409/12 条非标准值需业务确认映射，属数据治理问题而非纯技术问题，耗时不可压缩。
- **部门字符串引用点多**：“单位名称-科室名称”字符串在合同、用户、分管部门、部门管理、登录注入等多处拼接/解析，拆表需全链路排查。

### 5.2 实施建议

- 按 **A → B → C** 分期实施：先补约束与索引（低风险、可随时回滚），再按模块灰度拆分结构，每期独立回归。
- 每期迁移前执行整库备份（现有 `backups/` 机制可直接复用），并准备回滚 SQL。
- 建议以“数据口径一致性”（未支付/待支付/统计）为回归验收重点。

---

## 六、结论

当前系统在“业务可用”层面无性能问题（639 行全内存处理足够），但数据库设计整体停留在“Excel 电子表格直存”形态：无约束、无外键、无索引，多值字段、复合属性、自由文本与派生冗余并存。从数据库设计规范角度评价，**未达到第二范式，第一范式亦不完整**。

建议优先实施档位 A（完整性规范化，约 6–10 人天），以最低成本补齐约束与数据质量底线；档位 B 按业务需要分期推进；档位 C 在当前数据规模下不建议全量实施，可视后续数据量与查询复杂度再行评估。
