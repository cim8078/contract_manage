## 三、逐条改造建议与 AI 提示词

### A-01 合同编号唯一约束

**风险**：低　|　**工作量**：0.5 人天　|　**前置**：无

**建议内容**：为 `contracts.编号` 建立数据库级唯一索引，作为应用层重复校验的兜底。

```
【任务】为合同台账表 contracts 的“编号”列添加数据库级唯一约束（UNIQUE），使编号唯一性在数据库层兜底。

【背景】当前系统 contracts 表（SQLite，data/合同台账.db）的“编号”列无唯一约束，重复编号仅在应用层（app.py 新增/修改/导入接口）校验。目标：即使绕过 API 写入，数据库层也能拒绝重复编号。

【改动范围】仅修改 app.py 的 init_db() 迁移逻辑；不得改动任何业务接口行为与前端页面。

【实施要点】
1. 在 app.py 的 init_db() 中加入幂等迁移：CREATE UNIQUE INDEX IF NOT EXISTS idx_contracts_no ON contracts("编号")。
2. 迁移前先扫描存量重复编号（当前实测无重复，仍须校验）：若存在重复，脚本必须终止并输出清单，禁止静默删除。
3. “编号”为必填字段（639/639 非空），本项仅建唯一索引；NOT NULL 约束并入 A-05 处理。
4. 保持现有自增主键 id 不变，不引入新的业务主键。

【验收标准】
1. 执行 PRAGMA index_list(contracts) 能看到唯一索引 idx_contracts_no（unique=1）。
2. 直接向 contracts 插入已存在编号时，sqlite3 抛 IntegrityError（UNIQUE constraint failed）。
3. 通过 API 新增/修改/导入接口创建合法合同仍正常；重复编号仍由应用层返回友好错误提示（行为不变）。

【回滚】执行 DROP INDEX IF EXISTS idx_contracts_no，不影响已有数据。
```

### A-02 departments 复合主键

**风险**：低　|　**工作量**：0.5 人天　|　**前置**：无

**建议内容**：为 `departments` 表（当前无主键）建立“单位名称 + 科室名称”复合主键或等价唯一约束。

```
【任务】为 departments 表添加复合主键或唯一约束（单位名称, 科室名称），杜绝重复部门组合。

【背景】departments 表（13 行）当前无主键、无唯一约束，组合唯一性仅靠应用层保证。目标：数据库层兜底。

【改动范围】仅修改 app.py 的 init_db() 迁移逻辑；部门管理的增删改接口行为不变。

【实施要点】
1. SQLite 无法通过 ALTER TABLE 直接加主键，需重建表：CREATE TABLE departments_new（单位名称 TEXT NOT NULL, 科室名称 TEXT NOT NULL, PRIMARY KEY（单位名称, 科室名称）），拷贝数据后 DROP/rename（建议用 BEGIN…COMMIT 包裹，先备份）。
2. 迁移前校验存量无重复组合（当前 13 行无重复）；若存在重复须先输出清单终止迁移。
3. 保持现有读写接口使用“单位名称-科室名称”拼接字符串不变（字符串拼接属档位 B，本项不做）。

【验收标准】
1. PRAGMA table_info(departments) 显示复合主键；PRAGMA index_list(departments) 显示主键自动索引。
2. 插入已存在组合时报错；部门列表 API 与新增/删除部门回归正常。

【回滚】恢复旧表结构（迁移前备份的 DDL），数据无丢失。
```

### A-03 外键约束（FK）

**风险**：中　|　**工作量**：1–2 人天　|　**前置**：部门数据修复（见 A-08 配套）

**建议内容**：为 `attachments→contracts`、`users→departments`、`contracts→departments` 建立外键，并开启 SQLite 外键开关；引用删除采用 RESTRICT。

```
【任务】为系统添加外键约束：attachments.合同编号→contracts.编号、users.所属部门→departments(单位名称,科室名称)、contracts.所属部门→departments(单位名称,科室名称)，并全局开启 SQLite 外键开关。

【背景】当前三处引用均为“字符串外键”，无数据库约束，删除部门/用户可能产生悬空引用。目标：数据库层保证引用完整性。

【改动范围】app.py 的 _SCHEMA/init_db()（重建 contracts/users/attachments 三张表）与 _conn()（每个连接执行 PRAGMA foreign_keys=ON）；不改变任何业务接口行为与前端。

【实施要点】
1. SQLite 外键默认关闭，必须在每个连接建立后执行 PRAGMA foreign_keys=ON（修改 _conn()，对 db_query/db_exec 均生效）。
2. ALTER TABLE 无法添加外键，需重建三张表：建新表（含 FOREIGN KEY 声明）→ 拷贝数据 → 校验一致性 → 原子替换（rename）；重建前后执行整库备份。
3. 【前置】contracts.所属部门 存在 71 条“缺科室后缀”记录（如“湘潭市机关事务管理局后勤中心”），无法匹配 departments 组合，**必须先修复该数据**（归入 A-08 配套的部门数据修复步骤）再建外键；修复清单须输出供业务复核。
4. 引用动作使用默认 RESTRICT：存在合同/用户/附件引用的部门禁止删除；删除合同前附件已由应用层级联处理，保持现状。
5. attachments.合同编号 与 contracts.编号 当前 6 条全部匹配（已实测），迁移前仍须再次校验。

【验收标准】
1. _conn() 连接后 PRAGMA foreign_keys 返回 1。
2. 插入不存在的部门/合同编号被拒绝；删除被引用的部门被拒绝。
3. 附件上传/下载、部门管理、合同新增/修改/删除、归档等全流程回归正常。

【回滚】恢复重建前的备份数据库文件；或在重建脚本中保留旧表（_old 后缀）以备切换。
```

**风险**：低　|　**工作量**：0.5 人天　|　**前置**：无

**建议内容**：为 `contracts` 的常用查询列建立索引（编号、所属部门、经办人、采购时间、下次招采时间、是否归档）。

```

【背景】当前系统为全量内存查询（read_contracts 一次性加载），索引不影响现有功能，主要为后续优化与数据增长做准备。

【改动范围】仅 app.py 的 init_db()；不改变查询逻辑与接口。

【实施要点】

2. 索引命名规范：idx_contracts_<列名拼音或英文>，避免中文列名直接入索引名。

【验收标准】

【回滚】逐个 DROP INDEX 即可，无数据影响。
```

### A-05 CHECK 与 NOT NULL 约束

**风险**：中　|　**工作量**：1–2 人天　|　**前置**：A-08（枚举清洗）

**建议内容**：为金额列加 CHECK（≥ 0）、为必填列加 NOT NULL；枚举列 CHECK 仅在完成 A-08 清洗后启用。

```
【任务】为 contracts 表增加 CHECK 约束（金额非负、日期格式、枚举白名单）与 NOT NULL 约束（必填字段）。

【背景】当前表无任何 CHECK/NOT NULL，非法金额、空必填、非标准枚举均可入库。目标：数据库层拒绝非法数据。

【改动范围】app.py 的 _SCHEMA/init_db()（需重建表）；不得改变 API 行为，但允许 API 校验报错信息与数据库约束保持一致。

【实施要点】
1. 金额 CHECK：合同金额（万元）>= 0、结算金额 >= 0、已支付 >= 0、未支付 >= 0、决策的招标控制价 >= 0（空值允许，SQLite CHECK 遇 NULL 通过）。
2. NOT NULL：编号、项目分类、项目名称、采购方式、合同金额（万元）、资金来源、合同主要内容、经办人、所属部门（与前端必填星号一致）。
3. 枚举 CHECK：项目分类 4 值、采购方式 4 值、是否结算 是/否、资金来源 6 值、是否归档 是/否——**必须在 A-08 清洗完成后启用**，否则存量非标准值（113/409/12 条）会导致迁移失败；若业务暂缓清洗，则本项仅做金额/日期 CHECK 与 NOT NULL，枚举 CHECK 延后。
4. SQLite 加 CHECK/NOT NULL 需重建表（同 A-02 流程），重建前备份；迁移脚本须先校验存量满足新约束，输出违规清单。
5. 日期格式 CHECK：采购时间/开工/完工/竣工验收/下次招采时间 匹配 YYYY-MM-DD（含空值放行）。

【验收标准】
1. 插入负金额被拒绝；插入空必填被拒绝；插入非标准枚举被拒绝（若已启用）。
2. 现有 639 条存量全部满足新约束（迁移脚本零违规或已按清单修复）。
3. 新增/编辑/导入接口的合法数据全流程回归正常。

【回滚】恢复迁移前备份；约束全部失效仅需恢复旧表结构。
```

### A-06 字段类型与日期规范化

**风险**：中　|　**工作量**：1–2 人天　|　**前置**：业务确认（43 条非数字金额）

**建议内容**：`attachments.文件大小` 由 TEXT 改 INTEGER；日期列统一 `YYYY-MM-DD`；数值列存量文本转数值。

```
【任务】修正不规范字段类型：attachments.文件大小 TEXT→INTEGER；日期列统一为 YYYY-MM-DD；数值列（合同金额等）存量文本转 REAL。

【背景】attachments.文件大小 存文本；日期列存文本且格式混杂（实测含多种写法）；历史导入存在“合同金额为文本”（数据字典标注 43 条非数字）。目标：类型与格式规范化。

【改动范围】app.py 的 _SCHEMA/init_db()（重建 attachments 表、清洗日期列）+ 一次性迁移脚本；不改 API 行为。

【实施要点】

2. 日期：采购时间/开工/完工/竣工验收/下次招采时间/归档时间 统一 YYYY-MM-DD；存量无法解析的日期（实测 4 条异常）输出清单，由业务确认后回填，禁止静默置空。

【验收标准】
1. PRAGMA table_info(attachments) 显示文件大小为 INTEGER。
2. 全部日期列可被 app.py 的 parse_date() 正常解析；异常日期清单已确认处理。
3. 金额列无文本残留；列表/统计/导出金额一致（与迁移前对照抽查）。

【回滚】恢复迁移前备份；若仅需回滚类型，可重建旧结构并回填原值。

### A-07 schema_version 版本化迁移机制

**风险**：低　|　**工作量**：1 人天　|　**前置**：无

**建议内容**：新建 `schema_version` 表，将 `init_db()` 中 ad-hoc 迁移改为按版本号顺序执行、幂等的迁移列表。

```
【任务】建立数据库结构版本化迁移机制：新增 schema_version 表，将 init_db() 中散落的 ALTER TABLE 迁移改为按版本号顺序执行且幂等的迁移脚本列表。

【背景】当前结构变更靠 init_db() 内 ad-hoc ALTER TABLE（含历史兼容逻辑），无版本记录，无法审计与回滚。目标：结构变更可追溯、可重复执行。

【改动范围】仅 app.py 的 init_db() 及新增迁移辅助函数；不改变业务接口。

【实施要点】
1. 建表：CREATE TABLE IF NOT EXISTS schema_version（version INTEGER PRIMARY KEY, applied_at TEXT, description TEXT）。
2. 将现有迁移（资金來源、是否归档、归档人、归档时间、用户分管部门、列改名等）改写为迁移列表 migrations = [(1, desc, fn), (2, desc, fn), ...]，按 version > 当前最大版本依次执行，事务包裹，成功后写入版本记录。
3. 每次新增结构变更追加新版本号，禁止修改已执行的历史版本。
4. 启动时检测版本落后即自动执行；执行失败不记录版本、回滚事务并抛出错误。

【验收标准】
1. 全新库首次启动：全量迁移执行一次，schema_version 行数与迁移数一致。
2. 已存在库二次启动：无重复执行（幂等），版本号不变。
3. 手工模拟旧版本库升级成功；app.log 输出迁移记录。

【回滚】删除 schema_version 行即可强制重跑对应版本（迁移本身需保持幂等）；结构变更回滚仍依赖数据备份。
```

### A-08 枚举数据清洗

**风险**：中　|　**工作量**：2–3 人天　|　**前置**：业务确认映射

**建议内容**：按《数据字典表》标准值清洗存量非标准枚举（项目分类 113 条、采购方式 409 条、是否结算 12 条），并同步修复 71 条缺科室后缀的部门数据。

```
【任务】按《数据字典表》标准值清洗 contracts 存量非标准枚举，并修复“所属部门缺科室后缀”数据，为 A-03 外键与 A-05 枚举 CHECK 提供干净存量。

【背景】实测存量：项目分类 10 种写法（标准 4 种，非标准 113 条）、采购方式 30+ 种（标准 4 种，非标准 409 条）、是否结算 10 种（非标准 12 条）、所属部门 71 条缺科室后缀。目标：存量数据符合标准枚举，保证后续约束启用不失败。

【改动范围】一次性迁移/清洗脚本 + 数据更新；不得改动代码逻辑与前端选项。

【实施要点】
1. 项目分类映射（示例，最终以业务确认为准）：维修类/维修维护类→维护维修类；工程类→建设项目；委托支付函/造价咨询服务/补充协议→按业务确认归入标准类或保留待确认。
2. 采购方式映射（示例）：自行采购（电子卖场）/自行采购（公开招标）/自行采购（线下邀请）等 →自行采购；邀请招标/邀请招标（联合体投标）→按业务确认；全角/半角括号统一。
3. 是否结算：按季度结算/按月结算/按年度结算/按月支付/由具体实施的单项项目结算 → 是/否（或部分结算，按业务确认）；“/”→ 空。
4. 部门数据修复：71 条“所属部门=湘潭市机关事务管理局后勤中心”缺科室后缀，输出“编号+建议科室”清单由业务逐条确认后回填（不可静默猜测）。
5. 清洗前先导出“待确认清单”（编号、原值、建议值）供业务确认；确认后以映射表驱动更新，更新记录写入 operation_logs 或迁移日志；整个清洗过程保留备份。

【验收标准】
1. 清洗后项目分类/采购方式/是否结算取值全部为标准值（或业务确认的待确认值）。
2. 所属部门 71 条全部补齐科室后缀并可匹配 departments（13 个组合）。
3. 导出清洗前后对照表供业务复核；系统列表/统计/导出结果与清洗前对照一致（仅取值标准化，不影响统计口径）。

【回滚】恢复迁移前备份即可；映射表留存以便重跑。

## 五、回归验收清单

每条改造执行完成后，至少回归以下项目（覆盖三种角色：管理员 / 普通用户 / 查询用户）：

- 登录与首页五张统计卡片、到期提醒、待支付提醒（含更多/折叠）数值与改造前一致。

- 查询：组合筛选、重置、默认按编号降序；资金来源筛选。
- 导入导出：模板下载、导入预览、确认导入、查询导出（列名与数据一致）。
- 查询统计：九个统计维度结果与改造前对照一致（重点核对合同数、合同金额、未支付口径）。
- 数据权限：普通用户仅见本部门+分管部门；查询用户只读。
- 备份与日志：写操作自动备份、日志审计记录正常。

## 六、注意事项

- 所有结构变更（重建表、加约束、清洗数据）执行前必须先整库备份（现有 `backups/` 机制可直接复用），并准备回滚方案。
- 数据清洗类任务（A-08、A-06）必须先输出“待确认清单”交业务确认，**禁止 AI 静默猜测或丢弃数据**。
- SQLite 外键（A-03）需每个连接开启 `PRAGMA foreign_keys=ON`，否则约束不生效，属于最容易遗漏的点。
- 档位 B/C（多值拆表、列名英文化、字典表化）不在本清单范围，请勿在执行 A 档时顺带实施，避免范围蔓延。
