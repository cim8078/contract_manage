# A-01 建立数据库级唯一索引（contracts.编号）

> 目标：为合同台账表 `contracts` 的“编号”列添加数据库级唯一约束，使编号唯一性在数据库层兜底。
> 背景：当前系统 `contracts` 表（SQLite，data/合同台账.db）的“编号”列无唯一约束，重复编号仅在应用层（app.py 新增/修改/导入接口）校验。即使绕过 API 直接写入，数据库层也能拒绝重复编号。

**1. 修改范围**
- 仅修改 `app.py` 的 `init_db()` 迁移逻辑（A-01 块），未改动任何业务接口行为与前端页面。
- 未引入新的业务主键，自增主键 `id` 保持不变；“编号”的 `NOT NULL` 约束按任务约定并入 A-05 处理（本项仅建唯一索引）。

**2. 数据库结构修改（1 项）**
- 新增唯一索引（幂等）：

```sql
CREATE UNIQUE INDEX IF NOT EXISTS idx_contracts_no ON contracts("编号");
```

- 迁移前先扫描存量重复编号，若存在重复则终止并输出清单，禁止静默删除：

```sql
SELECT "编号", COUNT(*) AS c FROM contracts GROUP BY "编号" HAVING c > 1;
```

- 当前数据库实况（`PRAGMA index_list(contracts)`）：索引 `idx_contracts_no`，`unique=1`，单列 `编号`，非部分索引（partial=0）。

**3. 数据库记录修改（0 条）**
- 实测 639 条合同“编号”全部非空且无重复（重复数 0；编号 NULL/空串数 0），本次迁移未改动任何记录。
- 若某库存在重复编号，脚本会报错终止并列出重复清单，由人工处理后重跑；不会静默删除或合并数据。

**4. 解决的问题**
- 改动前：重复编号仅靠应用层接口（新增/修改/导入）逐个校验拦截，绕过 API（直接 SQL 写入、并发请求、导入逻辑漏洞）仍可能入库两条相同编号。
- 改动后：数据库层兜底——任何写入路径出现已存在的编号都会触发 `UNIQUE constraint failed`（`sqlite3.IntegrityError`）。
- 行为不变：应用层对重复编号仍返回友好中文提示（如“编号 'xxx' 已存在”）；合法新增/修改/导入不受影响。
- 附加收益：编号唯一为后续 A-03 外键（`attachments.合同编号 → contracts.编号`）提供了可靠的唯一引用目标，保证“一个附件编号只对应一份合同”。

**5. 后续迁移中的保持**
- A-03（三表外键重建）、A-05（contracts 重建并加 CHECK/NOT NULL）重建 `contracts` 表后，迁移脚本均执行 `CREATE UNIQUE INDEX IF NOT EXISTS idx_contracts_no ...`，该唯一索引始终生效（实测重建后仍存在）。

**6. 验收结果（已实测）**
1. `PRAGMA index_list(contracts)` 可见唯一索引 `idx_contracts_no`（unique=1）。
2. 直接向 `contracts` 插入已存在编号 → `sqlite3.IntegrityError: UNIQUE constraint failed: contracts.编号`。
3. API 新增/修改/导入合法数据正常；重复编号由应用层返回友好错误（行为不变）。

**7. 回滚方式**

```sql
DROP INDEX IF EXISTS idx_contracts_no;
```

- 回滚不影响任何已有数据；如需恢复唯一约束，重新执行第 2 节的 `CREATE UNIQUE INDEX` 语句即可。
