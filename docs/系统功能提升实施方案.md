> 文档定位：本方案将评审报告中各项提升建议细化为可执行的实施设计，逐项给出现状、目标、数据库变更、后端接口、前端交互、参考实现、验收标准与回退方案。**本方案不改动现有系统代码与数据**，供后续版本按 P0→P1→P2 顺序落地实施，每批实施完成后应在 1.3 节更新实施状态并同步相关手册。

## 一、实施总览

### 1.1 实施原则

- **兼容优先**：所有数据库变更采用“加列不改名、新增可空、幂等执行”方式，存量数据自动回填，不破坏现有 640 条合同、26 个用户、13 个部门组合的数据。
- **小步快跑**：按 P0→P1→P2 分批上线，每批独立可验收、可回退，避免一次性大版本风险。
- **留痕闭环**：删除、归档、清空提醒等敏感操作除二次确认外强制填写原因，并写入操作日志，满足经办与审批分离的机关管理要求。
- **文档同步**：每批上线同步更新《用户操作手册》《系统部署手册》《数据字典表》与《系统开发文档》。

## 二、P0 快赢（1 周内）

### 2.1 合同状态字段

**现状**：合同生命周期仅以“是否结算 + 是否归档”两个分散标志描述，无法表达“拟签、执行中、已完工、已结算、已终止”等状态，统计口径不统一，编辑权限由归档标志单独控制。

**目标**：新增“合同状态”字段，覆盖合同全生命周期，由状态统一驱动列表展示、统计口径与编辑权限，替代当前分散标志造成的口径混乱。

**数据库变更**（在 `app.py` 的 `init_db()` 中以幂等方式执行）：

```
ALTER TABLE contracts ADD COLUMN "合同状态" TEXT;
UPDATE contracts SET "合同状态" = CASE
  WHEN "是否归档" = '是' THEN '已归档'
  WHEN "是否结算" = '是' THEN '已结算'
  WHEN "是否结算" = '否' THEN '执行中'
  ELSE '执行中'
END
WHERE "合同状态" IS NULL OR TRIM("合同状态") = '';
```

**状态枚举**：拟签、执行中、已完工、已结算、已终止、已归档。

**后端变更**：

- `CONTRACT_COLUMNS` 在“是否结算”之后增加“合同状态”，使导出、导入模板、`c2r()` 输出同步覆盖；
- 新增合同默认状态“拟签”；新增/修改/导入时校验状态枚举，非法值拒绝；
- 状态联动：状态置为“已归档”时同步写入“是否归档/归档人/归档时间”；置为“已结算”时同步写入“是否结算=是”，保证新旧口径一致；
- 列表筛选增加 `status` 参数，与现有 `archived`、`is_settled` 筛选并存。

**前端变更**：

- 新增/编辑合同表单增加“合同状态”下拉选择；
- 台账列表增加“状态”列，按状态显示彩色徽章（拟签=灰色、执行中=蓝色、已完工=绿色、已结算=青色、已终止=红色、已归档=橙色）；
- 搜索筛选条件增加“合同状态”下拉。

**参考实现**：

```
STATUS_VALUES = ("拟签", "执行中", "已完工", "已结算", "已终止", "已归档")

def _apply_status(row):
    st = str(row.get("合同状态", "")).strip()
    if not st:
        row["合同状态"] = "拟签"
    if st == "已归档":
        row["是否归档"] = "是"
        row["归档时间"] = datetime.datetime.now().strftime("%Y-%m-%d %H:%M:%S")
        row["归档人"] = get_cur_user().get("姓名", "")
    if st == "已结算":
        row["是否结算"] = "是"
```

**验收标准**：

1. 存量 640 条合同按回填规则自动获得状态，无空值；
2. 新建合同默认“拟签”；状态枚举外值被拒绝；
3. 状态为“已归档”的合同只读（编辑、删除、附件上传均被拒绝）；
4. 列表可按状态筛选，导出 Excel 与导入模板均包含“合同状态”列；
5. 统计页可按状态分组统计（与 4.1 节配合）。

**回退方案**：删除“合同状态”列不影响其他列；回退旧版程序文件即可，无需数据迁移。

### 2.2 财务勾稽校验

**现状**：合同金额可为 0 或负数；“结算金额、已支付、未支付”三列可手工填出互相矛盾的数据；日期字段无先后逻辑校验，容易产生手工数据矛盾。

**目标**：金额非负且合同金额大于 0；未支付金额自动按“结算金额 − 已支付”计算；日期逻辑校验（完工不早于开工、竣工验收不早于完工、下次招采时间应晚于当前日期）。

**后端校验规则**（新增、修改、导入三处统一调用同一校验函数）：

| 校验项 | 规则 | 级别 |
|--------|------|------|
| 合同金额 | 必须大于 0 | 错误，阻止保存 |
| 结算金额 / 已支付 / 未支付 | 不能为负数 | 错误，阻止保存 |
| 未支付 | 结算金额与已支付均填写时自动计算为“结算金额 − 已支付” | 自动修正 |
| 完工时间 | 不早于开工时间（两者均填写时） | 错误，阻止保存 |
| 竣工验收时间 | 不早于完工时间（两者均填写时） | 错误，阻止保存 |
| 下次招采时间 | 应晚于当前日期（填写时） | 警告，提示确认 |

**参考实现**：

```
def validate_finance(row, warnings=None):
    errs = []
    amt = _num(row.get("合同金额（万元）"))
    if amt is not None and amt <= 0:
        errs.append("合同金额必须大于 0")
    for k in ("结算金额", "已支付", "未支付"):
        v = _num(row.get(k))
        if v is not None and v < 0:
            errs.append("%s 不能为负数" % k)
    s = _num(row.get("结算金额")); p = _num(row.get("已支付"))
    if s is not None and p is not None:
        row["未支付"] = round(max(0, s - p), 2)
    d1 = parse_date(row.get("开工时间")); d2 = parse_date(row.get("完工时间"))
    d3 = parse_date(row.get("竣工验收时间"))
    if d1 and d2 and d2 < d1:
        errs.append("完工时间不能早于开工时间")
    if d2 and d3 and d3 < d2:
        errs.append("竣工验收时间不能早于完工时间")
    return errs
```

**前端变更**：

- 表单保存前执行相同校验，错误字段红色提示；“未支付”字段在“结算金额、已支付”填写后自动回显计算值（只读）；
- 下次招采时间早于今天时，保存前弹出确认提示。

**验收标准**：

1. 合同金额 ≤ 0 时保存被阻止并提示；
2. 负数金额字段被阻止；未支付与“结算金额 − 已支付”不一致时自动修正；
3. 完工早于开工、验收早于完工被阻止；
4. 导入预览对上述错误逐条标红，导入时跳过错误行。

**回退方案**：校验为纯逻辑变更，无数据结构变更；回退旧版程序文件即可。

### 2.3 敏感操作复核留痕

**现状**：删除已强制填写原因；归档、清空下次招采时间仅有二次确认，未强制填写原因，操作日志详情为空，无法满足审计留痕要求。

**目标**：删除、归档、清空下次招采时间三类敏感操作统一强制填写原因，并将原因写入操作日志详情。

**后端变更**：

- `api_archive_contract`、`api_clear_remind` 增加必填 `reason` 字段，缺失返回 400“请填写操作原因”；
- 日志详情分别写入“归档原因：…”“清空提醒原因：…”。

**前端变更**：

- 归档确认、清空提醒（永久关闭）确认框增加原因输入框（`needReason: true`），未填写不允许确认。

**验收标准**：

1. 三类操作不填原因无法提交；
2. 日志审计中可查到“操作类型=归档/清空提醒”且详情包含原因；
3. 导出日志包含上述详情。

**回退方案**：纯逻辑变更，回退旧版程序文件即可。

## 三、P1 风控（2 周内）

### 3.1 密码存储加固

**现状**：密码使用 `SHA256(密码 + 固定盐)` 存储，无迭代次数，盐值固定并写死在源码中，抗暴力破解能力弱。

**目标**：改用 werkzeug 提供的 PBKDF2（`generate_password_hash` / `check_password_hash`），历史 SHA256 密码在首次成功登录时自动迁移为新算法，实现无缝升级。

**参考实现**：

```
from werkzeug.security import generate_password_hash, check_password_hash

def hash_pw(p):
    return generate_password_hash(p, method="pbkdf2:sha256:600000")

def verify_pw(p, stored):
    return check_password_hash(stored, p)

# 登录校验处：
if verify_pw(pw, stored_pw):
    if not stored_pw.startswith("pbkdf2:"):   # 旧 SHA256 哈希自动迁移
        db_exec('UPDATE users SET "密码"=? WHERE "用户名"=?', (hash_pw(pw), un))
```

**配套变更**：

- 新增用户、重置密码、修改个人信息全部改用 `hash_pw()`；
- 《系统部署手册》7.4 节密码重置脚本同步更新为 PBKDF2 版本；
- 升级后旧脚本生成的 SHA256 密码仍可登录一次并自动迁移，无需人工干预。

**验收标准**：

1. 新用户密码为 `pbkdf2:sha256:...` 格式；
2. 旧 SHA256 密码用户首次登录成功后被自动迁移；
3. 登录接口耗时增量在可接受范围（PBKDF2 迭代 60 万次约 0.1～0.3 秒）。

**回退方案**：`verify_pw` 兼容新旧两种格式，回退旧版程序文件即可，无需处理密码数据。

### 3.2 登录防护（失败锁定）

**现状**：登录无失败次数限制，可被无限暴力尝试；失败仅写日志。

**目标**：同一用户名连续失败 5 次锁定 15 分钟，锁定期间提示剩余时间；失败与锁定事件写入操作日志；远期可扩展图形验证码。

**参考实现**（单进程部署内存实现，多进程需改用 SQLite/Redis）：

```
_login_fail = {}   # {"admin": [失败次数, 锁定截止时间戳]}

MAX_FAIL = 5
LOCK_MINUTES = 15

def _check_lock(un):
    rec = _login_fail.get(un)
    if not rec:
        return None
    fails, until = rec
    if until and time.time() < until:
        return int((until - time.time()) // 60) + 1
    return None

def _record_fail(un):
    rec = _login_fail.get(un) or [0, 0]
    rec[0] += 1
    if rec[0] >= MAX_FAIL:
        rec[1] = time.time() + LOCK_MINUTES * 60
        rec[0] = 0
    _login_fail[un] = rec

# 登录成功时清空计数：_login_fail.pop(un, None)
```

**验收标准**：

1. 同一用户名连续输错 5 次后被锁定，提示“账号已锁定，请 X 分钟后再试”；
2. 锁定期间即使密码正确也拒绝登录；
3. 锁定事件写入操作日志；
4. 部署手册补充防火墙来源 IP 白名单与 HTTPS 建议。

**回退方案**：关闭锁定逻辑或回退旧版程序文件。

### 3.3 会话密钥环境变量化

**现状**：`app.secret_key` 为源码内置固定值，存在源码泄露导致会话伪造风险。

**目标**：优先读取环境变量 `SECRET_KEY`，未设置时回退内置值并输出启动告警。

**参考实现**：

```
import os
_DEFAULT_SECRET = "xtsgj_contract_manager_secret_key_2026"
app.secret_key = os.environ.get("SECRET_KEY", _DEFAULT_SECRET)
if os.environ.get("SECRET_KEY") is None:
    print("[WARN] 未设置环境变量 SECRET_KEY，请为生产环境配置随机密钥")
```

**部署配套**（详见《系统部署手册》8.2 节）：

- Windows：为服务账户设置用户环境变量 `SECRET_KEY`；
- Linux systemd：`Environment=SECRET_KEY=<随机密钥>`，密钥可用 `python -c "import secrets; print(secrets.token_hex(32))"` 生成；
- 修改密钥会导致所有已登录会话失效，需在低峰期执行并通知用户重新登录。

**验收标准**：

1. 设置环境变量后，会话加密使用新密钥（重启后旧会话失效）；
2. 未设置时启动输出告警，系统仍可运行。

**回退方案**：恢复内置默认值或回退程序文件。

2. 推迟后下次招采时间正确顺延，日志记录操作人与原因（如填写）；

### 3.5 附件管理规范

> 实施状态：已实施（2026-08-18）。系统设置新增“全局默认上传最大附件”（默认 20M，范围 1～200），上传超限将被拒绝；格式白名单与附件操作留痕保持原有功能。

**现状**：已有格式白名单（jpg/jpeg/png/gif/webp/bmp/pdf）与上传、删除留痕；附件目录已纳入备份范围；但无单文件大小限制，超大文件可能拖垮服务或占满磁盘。

**目标**：单文件不超过 20 MB；客户端预检 + 服务端强制校验；附件操作留痕保持现状。

**参考实现**：

```
ATTACH_MAX_BYTES = 20 * 1024 * 1024   # 20MB

# 服务端保存前：
f = request.files.get("file")
if f and f.content_length is not None and f.content_length > ATTACH_MAX_BYTES:
    return jsonify({"error": "附件大小不能超过 20MB"}), 400
# 保存后再校验实际大小：os.path.getsize(...) > ATTACH_MAX_BYTES 则删除并报错
```

**前端变更**：选择文件时校验 `file.size > 20MB` 并提示，减少无效上传。

**验收标准**：

1. 大于 20MB 文件在前端与服务端均被拒绝；
2. 正常附件上传、下载、删除不受影响；
3. 上传失败时临时文件被清理。

**回退方案**：回退程序文件即可。

## 四、P2 提效（1 个月内）

### 4.1 统计维度增强

> 实施状态：已实施（2026-08-19）。

**现状**：统计仅支持按部门、项目分类、经办人、时间四个维度，且只有合同数与合同金额两个指标，无法监控欠款风险与预算执行。

**实施内容**：

- 新增“按部门支付情况”“按项目支付情况”维度（接口 `pay_dept`/`pay_project`，归一化为 `unpaid` 逻辑）：按部门或项目汇总未支付金额；未支付取值优先使用“未支付”字段，为空时按“合同金额 - 已支付”自动计算；
- 新增“按部门预算执行情况”“按项目预算执行情况”维度（接口 `budget_dept`/`budget_project`，归一化为 `budget` 逻辑）：按部门或项目对比“决策的招标控制价”合计与“合同金额”合计，计算差额（合同金额 - 招标控制价）与偏差率（差额 ÷ 招标控制价 × 100%）；
- 分组方式并入统计维度名称，不再使用独立“分组维度”下拉；
- 统计筛选与查询条件联动：统一支持单位、科室、经办人、采购时间起止、年份过滤（`_stat_filter()`），口径与合同列表一致；
- 图表按维度分发：支付类维度图表1 对比未支付/已支付、图表2 对比合同金额/未支付；预算类维度图表1 对比控制价/合同金额、图表2 展示偏差率；两张图表仍可独立切换柱状/饼图/折线/环形；统计维度下拉顺序为：按部门、按时间、按经办人、按项目分类、按部门支付情况、按项目支付情况、按部门预算执行情况、按项目预算执行情况。

**后端变更**：`/api/statistics` 增加 `unpaid`、`budget` 分支与 `dim=dept|project` 分组参数，所有类型统一经 `_stat_filter()` 过滤。

**前端变更**：统计维度下拉增加“按部门支付情况”“按项目支付情况”“按部门预算执行情况”“按项目预算执行情况”并固定顺序（按部门、按时间、按经办人、按项目分类、部门支付情况、项目支付情况、部门预算执行情况、项目预算执行情况）；分组并入维度名称，移除“分组维度”下拉；新增“采购时间(起/止)”筛选；`makeChart` 支持多数据集，`renderCharts` 按维度分发图表。

**验收标准**：

1. 未支付金额：有“未支付”字段优先取字段值，为空按“合同金额 - 已支付”计算，与明细一致；
2. 预算执行：差额与偏差率计算正确，图表与明细一致；
3. 部门/经办人/时间范围筛选与统计结果联动，口径与合同列表一致；
4. 普通用户统计范围仅限本部门 + 分管部门。
### 4.2 编号规则化

**现状**：合同编号由经办人手工填写，易重号、易错号，缺少统一规则。

**目标**：提供“年度-类别-序号”自动编号辅助，如 `2026-FW-001`；类别代码：FW=服务类、WH=维护维修类、HW=货物类、JS=建设项目；编号仍允许手工修改，规则仅作辅助。

**后端变更**：

```
CATEGORY_CODE = {"服务类": "FW", "维护维修类": "WH", "货物类": "HW", "建设项目": "JS"}

@app.route("/api/contracts/next_number", methods=["GET"])
@login_required
def api_next_number():
    category = request.args.get("category", "")
    code = CATEGORY_CODE.get(category, "QT")
    year = datetime.date.today().year
    prefix = "%s-%s-" % (year, code)
    max_no = 0
    for c in read_contracts():
        n = str(c.get("编号", ""))
        if n.startswith(prefix):
            try:
                max_no = max(max_no, int(n[len(prefix):]))
            except ValueError:
                pass
    return jsonify({"number": "%s%03d" % (prefix, max_no + 1)})
```

**前端变更**：新增/编辑表单“编号”旁增加“自动编号”按钮，按当前选择的“项目分类”请求并回填。

**验收标准**：

1. 选择分类后点击自动编号，生成格式正确且不重复的编号；
2. 手工编号仍可修改，重复编号校验继续生效。

**回退方案**：回退程序文件即可。

### 4.3 台账批量操作

**现状**：延续性项目需逐条修改下次招采时间或归档，效率低。

**目标**：台账列表支持批量选择，提供“批量归档”“批量推迟下次招采时间（+7/15/30 天）”操作。

**后端变更**：

```
@app.route("/api/contracts/batch_archive", methods=["POST"])
@app.route("/api/contracts/batch_postpone", methods=["POST"])
# 入参：{"ids": ["row_1", ...], "reason": "..."} 或 {"ids": [...], "days": 15}
# 逐条复用单条权限校验；已归档/无权限的跳过并在结果中报告
# 返回：{"archived": n, "skipped": [编号, ...]} / {"postponed": n, "skipped": [...]}
```

**前端变更**：

- 列表增加复选框列与“全选本页”；
- 批量归档/批量推迟按钮（选中后可点击，管理员全量，普通用户仅本部门 + 分管部门）；
- 批量归档需填写原因（复用 2.3 节原因输入框）。

**验收标准**：

1. 批量操作仅影响有权限的合同；
2. 批量归档逐条写入日志并含原因；
3. 无权限与已归档合同在结果中列出（skipped），不静默跳过。

**回退方案**：批量操作使用既有单条写逻辑，回退程序文件即可。

### 4.4 导入增强

**现状**：已有模板下载、导入预览（逐条校验并分类“通过/警告/错误”）、重复编号跳过；错误行不导入。

**目标**：预览结果支持选择“仅导入通过行”或“跳过警告行继续导入”；导入结果报告逐条原因（当前已返回 `skipped` 列表，需在界面完整展示行号与原因）。

**后端变更**：`/api/contracts/import` 增加 `mode` 参数（`strict`=仅通过行，`warn_ok`=通过+警告行）；返回每条跳过记录包含行号与原因。

**前端变更**：预览弹窗增加导入模式选择；结果页展示逐条跳过明细（行号、编号、原因）。

**验收标准**：

1. 两种模式导入数量符合预期；
2. 跳过明细可追溯到行号与原因；
3. 与 2.2 节财务校验联动（错误行不导入）。

### 4.5 备份恢复操作规程与演练

**现状**：《系统部署手册》第 4 章已具备自动备份、手动备份、整体恢复、单条恢复方法；缺少定期恢复演练要求与记录。

**目标**：固化操作规程并加入演练机制：

- 自动备份：每次写操作前备份，保留 30 天（现状，保持）；
- 手动备份：每周一次，每月异地归档一次（现状，保持）；
- 恢复演练：每季度至少一次，记录演练时间、演练人、恢复方式、恢复数据量与结果，记录表见本方案 6.3 节；
- 演练内容：整体恢复演练（数据库 + 附件）、单条误删恢复演练。

**验收标准**：季度演练记录完整、可追溯；演练中发现的问题在一个月内闭环。

### 4.6 日志防篡改固化

**现状**：操作日志仅通过 `INSERT` 追加写入，系统内无修改/删除日志的界面与接口，导出动作自身留痕，基本满足审计要求。

**目标**：

- 保持“只追加、不可修改、不可删除”的设计，明确禁止新增日志编辑功能；
- 可选加固：将 `operation_logs` 定期导出归档并移出在线库，或在数据库层面对日志表做只读权限控制；
- 日志保留天数由“系统设置-日志保留天数”控制（默认 90 天），到期自动清理。

**验收标准**：API 层无任何修改/删除日志的入口；定期归档脚本可导出并清理历史日志。

### 5.2 发布与回滚流程

1. **发布前**：备份 `data/` 与 `backups/`；记录当前版本号与系统设置值；
2. **替换**：覆盖 `app.py`、`templates/index.html`、`static/`（如有变更）、`requirements.txt`（如依赖变更）；
3. **启动**：确认启动日志无错误，自动执行数据库迁移（幂等）；
4. **验证**：执行 5.1 回归测试清单；
5. **回滚**：停止服务 → 恢复备份 `data/` → 恢复旧版程序文件 → 重启 → 复测登录与合同列表。

### 5.3 上线前检查表（管理员）

- 修改默认密码，设置 `SECRET_KEY` 环境变量（P1 后）；
- 完成一次备份恢复演练并记录；
- 防火墙 / HTTPS / 来源 IP 白名单就绪；
- 操作日志导出并归档；
- 通知全体用户版本变更与操作变化（如有）。
